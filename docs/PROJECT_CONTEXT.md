# 서비스 기준 컨텍스트

실제 대상(2026-10-04 사용자 설명): 대광교회는 약 40명으로 어른 약 20명, 나머지는 청소년·청년이며 청년 중심 이용이 예상된다. 기능 수나 공동체 참여량보다 혼자서도 말씀·묵상·기도에 도움받는 경험을 우선한다. 기록·로그인·매일 참여를 강제하지 않는다. [작은 교회 경험 검토](small-church-experience.md)를 따르며 실제 사용자 검증은 아직 진행하지 않았다.

사용자 재정정(2026-10-04): 명료함은 콘텐츠마다 영역을 기계적으로 분리하라는 뜻이 아니다. 하나의 주제로 연결되는 여러 콘텐츠는 함께 구성하고, 메인은 이미지·배치·크기·여백의 변화로 디자인의 흐름을 만든다. 현재 구성은 환영/예배 안내 → 예배와 일상의 말씀 → 공동체 소식 → 교회 소개/첫 방문이다. 아래 ‘한 가지 메시지’는 이 의미로 해석한다.

사용자 디자인·운영 기준(2026-10-04 후속): 영역마다 한 가지 메시지만 전달한다. 불필요한 아치·장식은 배제하고 프리텐다드/노토산스를 기본으로 한다. 명조 강조가 필요한 경우에만 KoPub바탕을 사용하며 임의의 바탕체로 대체하지 않는다. 주보·주일 말씀·첫시간은 홈페이지와 앱에 중복 등록하지 않고 통합 관리자에서 같은 원본과 공개 상태로 관리한다. 과거의 말씀 채널별 독립 발행 정책을 대체한다. 구현·연결 제한은 [unified-content.md](unified-content.md)를 따른다.

사용자 정정(2026-10-04): 공식 이름은 **대한예수교장로회 대광교회**다. 교단명은 작게, 대광교회는 크게 표기한다. 앱은 따뜻하고 교회다운 이미지/아이콘을 보강하되 읽기 쉬운 구성을 유지한다. 전도회·소속 소식은 [설계 문서](groups-and-brand.md)를 따르며 관심 구독과 승인된 소속을 구분한다.

최신 개발 상태(2026-10-04): [88개 화면 점검표](mobile-screen-audit.md), [회사 PC 연결 점검표](company-pc-checklist.md), HANDOFF 최상단을 따른다. 가입·복구·계정·상담/심방·알림 화면은 로컬 테스트 API로 체험 가능하며 운영 어댑터는 비활성이다. 체험 문구·가상 인증번호·8자 비밀번호 기준은 확정 운영 정책이 아니다.

## 목적
독산대광교회 공식 앱. 말씀 → 묵상 → 기록 → 기도 → 교회생활을 연결한다. 매일 묵상 콘텐츠 「첫시간 주님께」가 중심이다. 공개 홈페이지는 교회소개/공개 콘텐츠를 맡고 통합 관리자는 홈페이지와 앱 콘텐츠를 운영한다. 향후 교적·재정 확장은 고려하되 지금 구현하지 않는다.

## 합의된 정책
- 비회원도 공개 콘텐츠를 이용한다. 첫 실행 강제 로그인 없이 개인 기능 접근 시 로그인한다.
- 성경 전문을 서비스에 싣지 않고 본문 위치(예: 요한복음 1:1)만 사용한다. 영상은 YouTube 기반이다.
- 개인 묵상과 기도는 기본 비공개이며 관리자가 임의로 열람할 수 없어야 한다.
- 공동기도제목, 개인 기도 기록, 목회상담/심방 요청은 성격이 다르다. 모든 기도를 제목→응답 추적 방식으로 강제하지 않는다.
- 중보기도 요청과 묵상 공유는 고려사항이 많아 보류했다. 사용자 재승인 없이 구현하지 않는다.
- 영상 재생/시청 상태와 묵상 작성 여부는 구분한다. 경쟁적 출석·점수화는 지양한다.
- 묵상은 당시 말씀과 연결한다. 개인 기도/일정/목회돌봄 접근 동선은 전체 IA와 함께 구체화해야 한다.

## UX 기준
원래 메인 IA: HOME / 말씀 / 소식 / 교회 / MY. 전체 screen inventory와 상세 UX를 먼저 확정하고 Low-Fi → 디자인 시스템 → High-Fi → 구현 순서를 따른다. 현재 일부 공개 묵상 화면과 서버 기반을 먼저 구현했으므로 전체 UX가 완료된 것으로 간주하지 않는다.

2026-10-03 재확인: 기존 Figma의 02 UX 명세(6:2), 03 App UI(6:3)에 화면 목록 및 88개 화면·상태 뷰가 이미 있다. 04 테마와 05 통합 관리자 설계도 존재한다. 위 제작 순서를 처음부터 반복하지 말고 기존 설계를 기준으로 미구현 부분을 연결한다. 초기 보관 페이지 6개만으로 전체 디자인 상태를 판단하지 않는다. 세부 미확정 정책과 실제 프로토타입/기능 검증은 구분한다.
