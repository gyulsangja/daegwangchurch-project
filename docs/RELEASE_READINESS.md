# 실제 연결과 출시 준비

기준: 2026-10-06. 사용자 요청으로 실제 Supabase 연결 및 후속 개발을 진행했다. **공개 출시 완료 문서가 아니다.**

최신 검증: 단위/체험 79개·격리 DB 통합 45개(합계 124개), 전체 타입/lint, 관리자 production 빌드 및 앱 웹/Android/iOS export 통과. 탈퇴와 알림 브라우저 흐름은 가짜 인증/개인 API로 검증했다. 실제 DB migration 12개가 적용되어 있다. 실제 탈퇴나 푸시 발송은 실행하지 않았다. Android APK/FCM 실기기 검증은 아직 없다.

## 사용자 답변과 결정 대기

- 예배 시간·연락처·모임명·담당자·상담 보관 기간: 미정. 기존 DB 자료를 임의로 확정하거나 예시로 채우지 않는다.
- 관리자 로그인: 사용자가 직접 로그인했고 인증된 관리 화면을 확인했다.
- 푸시 검증: 안드로이드 사용. 2026-10-09 Firebase Android 등록·설정 JSON 로컬 연결, Expo EAS 프로젝트 생성·로컬 UUID 연결, Android FCM V1 자격 할당 완료. HTTPS API·원격 빌드 환경·크론을 연결한 뒤 설치형 APK로 검증한다. 실제 수신은 미검증.
- 배포 방식/도메인 소유·호스팅 계정: 답변 대기. DB에 기존 대표 도메인 문자열이 있다고 소유권이나 DNS 연결을 확인한 것으로 보지 않는다.
- 신규 가입 정책·상담 전달 동의·탈퇴 보관 기준·푸시 수신 정책: 미정. 문구를 법적으로 확정된 약관처럼 임의 작성하지 않았다.

## 운영 설정 형식

`apps/admin/.env.local`에 설정한다. 정책을 실제로 승인하기 전에는 아래 플래그를 켜지 않는다. JSON 값은 환경 파일에서 한 줄로 작성하며 실제 개인정보를 문서나 Git에 넣지 않는다.

- `APP_GROUPS_ENABLED=true`: 실제 모임/담당자 등록과 승인 절차 확인 후 공개·소속 피드를 연다.
- `APP_MEMBER_CARE_ENABLED=true`, `APP_MEMBER_CARE_POLICY`: `{version, notice, retentionDays, adminIds}`. 기간은 접수 시점부터 계산한다. `adminIds`는 Supabase 사용자 ID가 아닌 관리자 프로필 ID다. 담당자·동의 안내·삭제 일정 확정 필요.
- `APP_ACCOUNT_ENABLED=true`, `APP_ACCOUNT_EMAIL_READY=true`, `APP_ACCOUNT_POLICY`: `{version, terms, privacy, care, deletion}`. SMTP와 가입 확인/복구 메일에 인증번호를 표시하는 템플릿, 이메일 확인 활성 여부를 먼저 검증한다.
- `APP_ACCOUNT_RATE_LIMIT_SALT`: 서버에서만 사용하는 충분히 긴 무작위 값. 현재 메일별 10분/10회 제한이며 Supabase 자체 제한도 적용된다. 배포 전 전체 요청 제한·봇 방지와 신뢰 가능한 프록시 경계 검토가 추가로 필요하다.
- 가입 대기 동의는 24시간 만료된다. `pending_registrations`의 만료 데이터 및 `inquiry_rate_limits`의 만료 계정 제한 데이터 삭제 스케줄을 배포 환경에 연결해야 한다.

만료 정리 명령: `npm run maintain:members`는 개수만 확인한다. `npm run maintain:members -- --apply`를 명시해야 만료된 행을 삭제한다. 상담 데이터는 유효한 돌봄 정책과 활성 플래그가 있을 때만 대상에 포함한다. 크론·작업 실행 계정은 배포 환경 확정 후 연결해야 한다. 확인되지 않은 환경에서 자동 실행하지 않는다.

2026-10-05 실제 DB에서 읽기 전용 실행을 검증했다. 만료된 가입 대기 및 요청 제한 행은 각각 0건이었으며 삭제는 실행하지 않았다.

가입 확인 후 프로필에는 동의 버전·시각·약관/개인정보 내용과 해시가 저장된다. 가입 확인과 DB 기록은 서로 다른 시스템이므로 제공자 확인 성공 후 DB 장애가 발생하는 복구 시나리오는 실제 환경에서 추가 검증해야 한다. 공개 가입은 탈퇴 기능 완성과 함께 출시한다.

## 검증 재실행

기존 `npm test`, `npm run type-check`, `npm run lint`, `npm run check:boundaries`를 실행한다.

Docker 없는 Windows에서는 PostgreSQL 공식 Windows 배포 경로에서 받은 EDB 바이너리를 `test-results/postgres/runtime/pgsql`에 두고 Bash에서:

```bash
TEST_POSTGRES_BIN="$PWD/test-results/postgres/runtime/pgsql/bin" npm run test:integration:local
```

테스트는 새로운 임시 로컬 클러스터를 루프백에만 열고 독립 DB에 migration을 적용한 뒤 종료한다. 서버 환경 파일을 읽지 않으며 실제 Supabase를 테스트 대상으로 사용하지 않는다. 테스트용 가상 회원/콘텐츠는 이 DB에만 들어간다. 바이너리·데이터·로그는 Git 제외 폴더에 둔다.

공식 배포 경로: [PostgreSQL Windows](https://www.postgresql.org/download/windows/), [EDB 바이너리](https://www.enterprisedb.com/download-postgresql-binaries). 인증 구현 참고: [Supabase OTP 검증](https://supabase.com/docs/reference/javascript/auth-verifyotp), [메일 템플릿](https://supabase.com/docs/guides/auth/auth-email-templates).

`npm run check:release`는 값 자체를 출력하지 않고 현재 로컬 설정의 출시 차이를 표시한다. 현재 localhost·계정 삭제·실기기 검증 항목이 미완료로 나오는 것이 정상이며, 이 명령을 통과했다고 전체 출시 검증이 완료되는 것은 아니다.

## 출시 전 반드시 남은 작업

1. 기존 자료의 실제 여부 확인, 검토된 말씀·주보 등록 및 실제 관리자 저장 → 홈페이지/앱 반영 확인.
2. 두 실제 테스트 회원으로 로그인·개인 기록·토큰 만료·프로필을 검증. 외부 메일 발송/인증/복구 확인.
3. [회원탈퇴 처리 기준](account-deletion.md)의 지원 삭제 범위·영수증/백업 보관 정책 승인, 서버 전용 키·재처리 주기 작업 연결, 격리된 Supabase 계정 종단간 검증. 공개 가입은 탈퇴 준비와 함께 활성화한다.
4. 정책 승인 후 상담·소속 기능 활성, 만료 데이터 삭제 스케줄 및 감사·백업·복구 점검.
5. 구현된 푸시의 Expo/FCM 계정·자격, 배포 HTTPS API와 Supabase Cron/Vault 연결. 본인 안드로이드 APK에서 권한·앱 종료 수신·로그아웃/계정 전환·중복·일정 변경을 검증한 뒤 교인에게 안내. iOS는 별도 Apple 서명/APNs 준비 필요.
6. 호스팅·도메인 소유 확인, 각 프로젝트 HTTPS 환경 설정, DB 백업/복구 리허설, 배포 오류 관측과 롤백 절차.
7. 실제 교인 사용성, Android/iOS 서명 계정·앱 식별자·스토어 정보, 개인정보/계정 삭제 안내. 스토어 제출은 미실시.
8. 의존성 감사의 남은 항목 검토. Next.js는 보안 수정 버전으로 갱신했지만 Expo/Prisma 개발 도구 등은 호환성 검증 없이 강제 메이저 변경하지 않는다. 최신 감사 출력은 `test-results/local-servers/dependency-audit.json` 참고.
