# 계정 삭제·복구 검증과 운영 적용 전 조건

2026-11-16 갱신. 실제 테스트 Supabase에서 가입·복구·탈퇴와 인증 계정 삭제까지 검증했다. 상세는 [실제 검증 기록](release-test-2026-11-16.md)을 따른다.

운영 읽기 전용 점검에서 삭제 대기 0건, 고아 계정 연결/상담 인계 0건, 활성 목회 권한과 삭제 기록의 충돌 0건을 확인했다. pg_cron·pg_net·Vault가 설치되어 있다. 운영의 009·010 SQL은 아직 미적용이다. Supabase Free 백업 화면은 자동 백업 미제공으로 표시되었다. 다른 PC·외부 저장소의 수동 백업 유무는 사용자 답변 대기다. 사용자는 실제 백업 기간을 확인한 뒤 최소 삭제 기록 보관 기간 제안에 따르기로 했다.

## 확정한 정책

탈퇴 시 개인 묵상·기도·교인 확인·상담·심방 자료 삭제. 상담·심방은 일반 보관 상한 5년이며 탈퇴 시 남은 기간과 관계없이 삭제한다. 지원 수신 이메일 및 조직 증빙은 미정. 삭제 영수증·백업·로그 기간은 별도 확정 필요.

## 확인된 삭제 경계

- 기존 서비스는 본인 자료 삭제와 탈퇴 작업 생성이 한 DB 트랜잭션이다. 교인 확인은 프로필 FK cascade. 인증 계정 삭제는 재시도 worker가 수행하며 `accepted`는 최종 완료가 아니다.
- 운영 통합 접수함은 앱 요청 원문을 공유 조회한다. 본문을 복제하지 않는다.
- 별도 `ministry.account_links`, `ministry.care_intakes`, 인계로 생성된 `ministry.pastoral`은 기존 코드만으로 남을 수 있다.
- 준비한 `009_member_deletion_links.sql`은 프로필→계정 연결, 요청→인계의 FK cascade와 인계 삭제→파생 목회 일정 삭제를 추가한다. 일정 본문·변경 이력도 같은 행에서 삭제된다. 기존 독립 교적·수기 목회 기록을 앱 탈퇴만으로 자동 삭제하지 않는다. 이 별도 기록에 앱 개인 내용을 수기로 복사한 경우 담당자 확인이 필요하다.
- 기존 고아 연결이 있으면 migration은 실패하도록 설계했다. 자동으로 기존 자료를 지우며 통과시키지 않는다. 운영 적용 전 고아 연결 수와 파생 일정의 범위만 조회하고 처리안을 승인받는다.
- `010_member_deletion_access.sql`은 활성 목회 권한 보유자의 삭제 접수를 DB에서 차단하고, 삭제 중인 계정의 권한 부여를 같은 계정 잠금으로 차단한다. 비활성화 후 삭제 가능하며 SQL 회귀 검증을 통과했다. 테스트 Supabase 적용 완료.
- 비활성 과거 CMS 관리자에 대한 관리자 요청 삭제가 Auth 일시 장애 뒤 worker에서 계속 막히던 문제를 수정했다. 활성 관리자 보호는 유지하고, 비활성 과거 관리자의 재시도 완료를 실제 로컬 PostgreSQL로 검증했다.

## 백업 복원 절차 — 아직 운영 검증 안 됨

1. 실제 Supabase 백업/PITR·Vercel/인증 로그·수동 덤프의 보관 기간과 접근자를 확인한다. 현재 대시보드 설정은 미확인이다.
2. 백업 안의 삭제 데이터를 즉시 부분 삭제할 수 있다고 고지하지 않는다. 보관 만료와 접근 차단, 복원 시 재삭제 절차를 명시한다.
3. 복구는 외부 접속이 차단된 환경에서 수행한다. 해당 백업 시점 이후의 삭제 처리 목록과 대조해 앱 개인 자료·계정 연결·인계 일정을 다시 삭제하고 인증 계정 부재를 확인한다.
4. 오래된 백업에 이미 사라진 탈퇴 영수증이 없을 수 있다. 영수증을 백업보다 먼저 없애지 않도록 기간 관계를 검토하고, 독립적으로 보존할 최소 삭제 목록의 근거·기간·접근자를 확정한다. 현재 `receiptRetentionDays`를 임의로 정하지 않는다.
5. 다른 회원 자료가 유지되고 탈퇴자의 로그인·토큰·자료 조회가 거부됨을 확인한 뒤에만 서비스 연결을 복원한다.

현재 `backup:ministry`는 로컬 SQLite 가상 자료 백업용이다. 운영 Supabase 백업 검증 증거로 사용할 수 없다. 실제 백업 복원 시험은 승인된 격리 프로젝트와 가상 계정으로 수행한다.

## 승인 요청 전에 확보할 증거

- 로컬 lifecycle HTTP 시험(가상 인증), 실제 로컬 PostgreSQL 삭제/권한 시험, 목회 스키마 cascade 시험을 구분하여 기록.
- 별도 테스트 Supabase의 SMTP/OTP·세션 폐기·인증 계정 삭제·worker 재시도 종단간 검증 필요. 로컬 가짜 제공자 시험을 실제 메일 수신/삭제 검증으로 보고하지 않는다.
- 운영 변경 후보: reviewed 정책, 복구 설정, 삭제 worker 스케줄·장애 확인, 009 migration, 앱·API 버전. 영향: 준비되지 않은 상태에서는 새 코드가 가입을 닫는다.
- Git push/운영 설정/DB 적용은 별도 승인 후 수행. 테스트 배포·서명·스토어 제출 승인은 포함하지 않는다.

## 자동 처리 배포 준비

`POST /api/internal/deletions`는 별도 `APP_DELETION_WORKER_SECRET` Bearer 인증과 기존 삭제 정책 설정을 확인한다. 호출당 1건을 처리해 서버 실행 시간을 제한하며 재시도 lease와 지연은 기존 삭제 서비스가 관리한다. 응답의 completed/deferred/pending/oldestPendingAt으로 결과를 확인한다. 개인정보나 제공자 오류 원문을 반환하지 않는다. 실패 시 503을 반환한다.

`scripts/supabase-deletion-cron.sql`은 Vault의 전용 URL·비밀값을 이용한 5분 간격 실행 준비안이다. 운영 적용 전 HTTPS endpoint·정책·별도 키를 설정하고, net._http_response의 HTTP 상태와 응답 본문을 함께 확인한다. cron SQL 성공만으로 삭제 성공으로 판단하지 않는다. 현재 운영 스케줄은 푸시와 상담 만료 두 개이며 삭제 스케줄은 추가 전이다.

운영 활성화는 실제 백업 보관 범위와 삭제 기록 기간 확정, 복원 후 재삭제 검증, 검토한 약관·개인정보 정책, 009/010 적용, 서버 비밀 설정, 배포와 스케줄 검증을 함께 수행한다. 가입 정책이 빠진 새 API만 배포하면 가입이 닫히므로 함께 반영해야 한다.
