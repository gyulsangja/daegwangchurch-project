# 목회시스템 개발 기준

확정일: 2026-10-21. 기존 저장소 안의 `apps/ministry`, 로컬 포트 3002, 독립 배포 단위. 기존 website/admin/mobile은 유지한다. 앱은 Android 1.0.1 개발용 배포에서 당분간 유지한다.

## 현재 단계

교적 업무 검토용 로컬 개발 기반. 현재 명부 관리 방식/열 이름은 사용자도 정확히 모르는 상태다. 실제 교적 자료를 읽거나 기존 회원을 자동 이관하지 않는다. 개발본은 명시적인 로컬 실행에서만 가상 데이터를 제공한다. 2026-10-23부터 이 PC의 SQLite 개발 DB에 지속 저장한다. 로그인·운영 DB·실제 권한 계정은 후속 단계이며 이 개발본을 실사용 시스템으로 배포하지 않는다.

## 범위와 화면

1. 홈: 전체/재적/소속 미배정, 최근 등록, 교인 찾기 바로가기.
2. 교인: 이름 검색, 상태·소속 필터, 페이지네이션. 이름으로 상세 진입. 이름/상태만 필수.
3. 교인 상세: 기본, 가족, 소속, 변경 이력 탭. 수정 후 같은 교인으로 복귀. 상세 목록 복귀는 기존 검색 조건 유지.
4. 조직: 조직별 구성원 및 담당 구조. 현재 개발본의 조직명·직분·상태는 가상 설정값이며 대광교회의 확정 조직이 아니다.
5. 후속: 가족 관계 편집, 조직 트리 편집, 명부 가져오기·내보내기, 운영 설정. 미구현 기능 버튼은 실제 동작처럼 표시하지 않는다.

등록/수정은 `.local/ministry/review.sqlite`에 저장된다. 서버 재시작/개발 리로드로 초기화하지 않는다. 브라우저 저장소에는 저장하지 않는다. 기존 메모리 개발본의 초기화 안내는 이 내용으로 대체한다.

| ImportJob | churchId, actorId, 검증 결과, 확정 상태, 멱등키 |

운영 PostgreSQL 구현은 packages/database 안에서 별도 스키마/마이그레이션 경로와 전용 접속 역할을 정한다. 기존 운영 DB migration에 자동 포함하지 않는다. `(church_id, id)` 복합키/외래키로 타 교회 연결 차단, 활성 소속 중복 방지, version 조건 UPDATE, 변경+감사 원자적 트랜잭션 필요. 공개 홈페이지 DB 역할에는 교적 스키마 접근을 주지 않는다. 이를 보장할 수 없으면 별도 DB로 분리한다. 실제 접속 권한 확인 전 같은 DB 사용을 확정하지 않는다.

현재 개발 액터는 서버에서 고정한 가상 관리자이며 로그인 구현이 아니다. 운영에서는 검증된 세션의 churchId/권한을 서버가 결정하고 요청 본문의 churchId/actorId를 신뢰하지 않는다. 두 가상 교회를 통한 접근 경계 테스트를 먼저 유지한다. 재정·목양 비밀 기록·개인 묵상은 자동 열람 범위에 포함하지 않는다.

## API 계약과 단계별 백로그

- GET /api/v1/members?q=&status=&organizationId=&page= : 목록, 전체 건수, 페이지 크기.
- POST /api/v1/members : 이름/상태/선택 정보. 교회·작성자·ID는 서버 지정.
- PATCH /api/v1/members/:id : 수정값과 version, 오래된 수정은 409, 범위 밖 ID는 404.
- 이번 API는 로컬 개발 전용. 운영/비활성 503, 외부 origin 403, 잘못된 입력 422. 실제 사용 전 인증 어댑터로 교체하고 조직/필드 권한을 유지한다.

다음 순서: ① 명부 항목/실제 조직 확인 ② 운영 인증·교회 역할 승인 ③ 교적 DB/트랜잭션 어댑터 ④ 가족/조직 편집 ⑤ 엑셀 미리보기·중복 후보·확정 반영 ⑥ 반출/감사/백업 복구 검증 ⑦ 실제 담당자 검증. 기존 앱·콘텐츠 연동은 그 이후.

미확정: 실제 명부 항목, 교적 상태 정의, 가족 대표 개념, 담당자 역할, 보관/파기 기준, 개발/운영 DB, 백업 정책. 주민등록번호·신앙 점수는 수집하지 않는다. 상담·심방은 2026-10-22 요청에 따라 가상 자료용 입력을 추가했다. 임시 기본안을 실제 교회 정책으로 취급하지 않는다.

## 연도별 운영과 개인 이력 (2026-10-22)

2026-10-23 사용성 개선: 구성원 배정은 조직별 일괄 편집이 기본이다. 조직별 `roleCodes`로 전도회·교회학교 등의 역할을 제한하고 설정에서 추가/선택한다. 역할별 담당자 표시, 검색 결과 일괄 추가, 선택 구성원 필터, 변경 요약 제공. 기존 개인별 편집은 보조 기능. `/api/v1/years/:year/roster`는 조직 하나의 명단만 검증 후 교체하며 다른 소속과 직분을 유지한다. 이름 검색에 가려진 사람도 유지하고, 여러 요청을 반복해 부분 저장하지 않는다. 조직 역할은 구성원당 하나이며 같은 역할을 여러 명에게 배정할 수 있다. 연간 역할 제한은 실제 활동의 과거 역할 기록과 별개다. 브라우저 추가 검사: `node tests/ministry-roster-browser.mjs`.

- 환경설정: 교회 이름, 직분, 교적 상태, 조직 유형·역할, 상하위 조직을 편집한다. 교회학교/봉사팀 유형과 학생/교사/부장/봉사자 역할 제공. 같은 교인은 여러 조직에 참여할 수 있고 조직별 역할을 지정한다. 역할은 로그인 접근 권한과 다르다.
- 연도: 기존 연도 복사 → 준비 → 배정 검토 → 명시적 운영 전환 → 이전 연도 마감. 준비 중에는 현재 교적이 바뀌지 않는다. 마감 연도는 수정 금지. 새 구성원 누락, 사용 중 코드 삭제, 순환 조직, 낡은 version 차단. 연도 내 배정 전후 스냅샷도 남긴다. 전환 시 기존 리더의 이전 연도 범위는 무효화한다.
- 교인 상세 ‘교회생활 기록’: 실제 날짜의 직분/교적 변동, 새가족·교육·정착 과정, 조직 역할별 활동 시작/종료, 예배/모임 출석, 상담/심방과 후속 날짜. 새가족 과정과 재적/이적은 독립이다. 과거 이력 추가는 더 최근 직분/상태를 덮어쓰지 않는다. 같은 날 변경은 마지막 등록이 우선한다. 미래 발생일은 아직 불허한다.
- 실제 취임일을 모르는 기본정보·연도 배정 수정은 변경 당일의 ‘실제 변동일 확인 필요’ 기록으로 표시한다. 과거 취임일이 자동 추정되는 것은 아니다. 현재 fixture의 최초 직분·상태는 입력 시점이 확인되지 않아 역사적 취임 사실로 생성하지 않는다.
- 연간 편성표는 계획/현재 배정, 소속·봉사 기간은 확인된 실제 활동 이력이다. 기간 기록만 입력한다고 편성표를 자동 변경하지 않는다. 이 구분을 화면에서 안내한다. 실제 DB 단계에서 편성 적용일·활동 종료를 통합하는 트랜잭션을 추가한다.
- 상담은 서버 Actor의 명시적 CARE 권한 필요. ADMIN이어도 권한 없으면 본문이 반환되지 않는다. 로컬 검토 액터만 CARE 부여. 상담 원문은 일반 교적 응답·감사 필드에 포함하지 않는다. 운영 담당자 배정, 보존/파기 실행, 암호화·백업은 실제 인증/DB 단계 필수이며 아직 미구현.
- 출석 중복(교인·날짜·조직·예배명), 같은 역할의 활동 기간 겹침 차단. 출석/활동/상담 오입력은 사유를 남겨 정정 처리하고 올바른 내용을 재등록한다. 원문과 정정 행위는 남으며 실제 삭제/파기 기능과 다르다. 결석은 명시 입력한 경우만 인정한다.
- 신규 API: `/api/v1/years` 및 연도별 configure/assignments/activate, `/api/v1/members/:id/records` GET/POST와 `/:recordId` PATCH 정정. 로컬 접근 제한 동일, production에서는 503. 운영 DB와 기존 서비스에는 연결하지 않았다.
- 추가 브라우저 검사: `node tests/ministry-records-browser.mjs` (교회학교 생성·교사 배정·출석·상담 저장·모바일 폭). 연도 상태 전환, 과거 직분, 상담 권한, 중복·기간 충돌은 `npm run test:ministry`에서 검증한다.

## 로컬 저장·백업 (2026-10-23)

- Node.js 24 이상 필요. [Node.js SQLite API](https://nodejs.org/download/release/v26.5.1/docs/api/sqlite.html)의 DatabaseSync/backup 사용. 새 npm 네이티브 모듈 설치 없음. `packages/database/src/ministry-local.ts`에 운영 Prisma와 분리한 어댑터 추가. 기존 DATABASE_URL·Supabase·운영 migration을 사용하지 않는다.
- 현재 저장 방식은 교적 상태·연도별 설정·개인 기록을 하나의 버전된 스냅샷으로 저장하는 **개발용 SQLite 어댑터**다. 운영 PostgreSQL 정규화 모델/복합 FK/RLS/암호화/인증 구현을 대체하지 않는다. 실제 개인정보 입력 금지.
- 도메인 호출마다 `BEGIN IMMEDIATE`로 최신 상태를 읽고, 권한/입력/version 검사 후 데이터와 감사 기록을 같은 트랜잭션에 저장한다. HTTP 본문 파싱·비동기 네트워크 요청은 잠금 안에서 실행하지 않는다. 실패 시 롤백하고 메모리 객체를 버린다. 복수 연결에서도 낡은 상태로 덮어쓰지 않는다.
- 형식 버전·체크섬 검사. 지원하지 않는 형식이나 손상된 DB는 오류를 반환하며 자동 초기화하지 않는다. 체크섬은 손상 감지용이며 암호화나 악의적인 변조 방지 수단이 아니다. 레코드별 정규화 및 대용량 최적화는 운영 어댑터 단계.
- 기본 파일 `.local/ministry/review.sqlite`, WAL/SHM 및 `backups/` 모두 `.local/` 아래. Git 제외. 다른 PC로 Git pull해도 이 개발 DB는 자동 복사되지 않는다. 최초 DB 생성 시에만 가상 fixture로 시작한다.
- 백업: 저장소 루트에서 `npm run backup:ministry`. 기본 개발 DB를 SQLite 백업 API로 `.local/ministry/backups/`의 새 파일에 저장한다. 기존 백업을 덮어쓰지 않는다. 복구 검토는 원본을 덮어쓰지 말고 서버를 종료한 뒤 백업 절대경로를 `MINISTRY_LOCAL_DB_PATH`로 지정해 별도 실행한다. 운영 백업/보존 정책은 별도 설계 필요.
- 저장소 검증: `tests/ministry-storage.test.ts`에서 별도 프로세스 읽기, 전체 상태 재구성, 백업 파일 읽기, 실패 롤백, 손상 시 비초기화, version 충돌 및 교회 경계를 검사한다.
