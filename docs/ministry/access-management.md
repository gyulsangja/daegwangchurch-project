# 목회시스템 사용자·권한 운영

2026-10-27 구현. 홈페이지·성도 앱 계정과 교적은 별개이며, 목회 권한은 `ministry.access_grants`에 명시적으로 등록한다. 앱 회원가입을 막거나 CMS 관리자에게 목회 권한을 자동 부여하지 않는다.

## 관리자 이용

- `/users`: 사용 중/이용 중지/초대 관리/최근 변경 이력. 이름·이메일 검색 및 팝업 편집.
- 최고관리자는 사용자와 교회 체계를 관리한다. 상담·심방·기도·계획은 CARE, 문서 출력은 can_print, 가구·목회활동 보관은 can_delete를 별도로 선택한다. 여기서 ‘삭제’는 기존 기록을 지우는 계정 영구삭제 기능이 아니다.
- 교적·목회 담당자는 기존 OFFICE 권한으로 교적·가구·교육·출석을 관리한다. 민감기록은 별도 허용한다.
- 부서 담당자는 현재 운영 연도에 명시한 조직의 명단과 출석만 이용한다. 연락처·주소·가구·개인 상담·교육 이력은 열람하지 못한다. 연도 전환 후에는 최고관리자가 해당 연도를 다시 지정한다. 과거 출석 기록도 지정된 조직 범위로 제한한다.
- 상태를 이용 중지로 바꾸면 이후 요청부터 접근을 차단한다. 진행 중인 짧은 트랜잭션은 먼저 완료될 수 있다. 앱 계정과 교적·작성 이력은 유지한다.
- 마지막 최고관리자와 본인 최고관리자 권한 회수를 막는다. 버전 충돌 시 새로 읽고 저장한다. 변경 사유/처리자/변경 전후를 기록한다.

## 초대와 이메일

1. 최고관리자가 이름·이메일·업무·권한을 입력한다.
2. 7일 유효한 링크를 생성해 본인이 초대 대상에게 전달한다. 링크 원문은 DB와 감사에 저장하지 않고 SHA-256 해시만 저장한다. URL fragment를 사용해 요청 URL/Referer에 초대 토큰이 남지 않게 한다.
3. 초대 대상은 이메일 확인 링크를 요청한다. Supabase 이메일 링크를 요청한 브라우저에서 열면 PKCE 세션이 생긴다.
4. 확인된 이메일이 초대 대상과 일치할 때 수락한다. 기존 계정은 그대로 쓰고, 신규 계정도 이메일 확인 후에만 목회 권한이 생긴다.
5. 인증 앱 연결은 선택이다. 비밀번호가 없는 신규 이메일 링크 계정은 ‘비밀번호 찾기’로 비밀번호를 설정한다. 권한 변경 시 현재 비밀번호를 다시 확인한다.

재발급은 기존 링크를 폐기한다. 취소·만료·이메일 불일치·초대자의 관리자 권한 회수 시 수락 불가. 조직 편성 연도가 달라지거나 해당 조직이 사라진 초대도 수락 불가. 이메일 요청은 초대별 60초 간격과 하루 5회 제한에 Supabase 자체 제한을 추가 적용한다. 관리자에게 초대 메일을 자동으로 보내는 별도 메일 서비스는 추가하지 않았다.

Supabase Authentication → URL Configuration → Redirect URLs에 현재 `MINISTRY_ORIGIN` 기준 다음 주소가 필요하다. 기존 앱·홈페이지 주소와 Site URL은 유지한다.

```
http://localhost:3002/auth/callback?flow=invite
http://localhost:3002/auth/callback?flow=recovery
```

운영 도메인을 정하면 해당 HTTPS 주소의 동일한 callback도 추가한다. `127.0.0.1`로 로그인과 메일 요청을 혼용하지 않는다. 메일 링크는 요청했던 브라우저에서 열어야 PKCE verifier가 일치한다. Authentication → Emails의 발송 설정/SMTP와 실수신을 확인해야 한다. 기본 메일 서비스의 수신 대상·발송량 제약이 있을 수 있으므로 실제 직원 초대 전에 승인된 이메일로 확인한다. 비밀 SMTP 값은 Git이나 채팅에 남기지 않는다.

## 로그인 및 보안

- `/login`: 이메일·비밀번호 로그인, `/forgot-password`: 이메일 재설정 요청.
- `/account/security`: 인증 앱 연결/6자리 코드 검증, 현재 비밀번호 또는 서명된 10분 복구 의도를 통한 비밀번호 변경.
- 일반 로그인은 이메일·비밀번호만 사용한다. MFA는 선택이며, 등록을 완료한 계정만 이후 AAL2를 요구한다. 권한 변경 SQL은 AAL2 또는 서버에서 재검증한 현재 비밀번호가 필요하다. 일반 앱에 대한 인증 정책을 전역 변경하지 않는다.
- HttpOnly, SameSite 쿠키, 운영 HTTPS Secure, 동일 출처 POST 검증, 허용된 고정 callback 목적지, 비밀번호/복구 쿠키/초대 원문 로그 제외.
- 인증 기기 분실 시 본인 확인을 거친 Supabase 운영 담당자의 복구가 필요하다. 웹 관리자에게 타인의 MFA 해제 버튼을 제공하지 않는다. 이미 설정한 개인 MFA를 임의로 해제하거나 공개된 공통 비밀번호를 만들지 않는다.
- 전 계정 하드삭제, 재정 권한, 여러 교회의 셀프 개설은 현재 범위에 넣지 않았다. 교회별 분리 키와 권한 모델은 유지한다.

## 운영 적용 결과

- `002_access_management.sql`과 `003_optional_mfa.sql`을 실제 비공개 ministry 스키마에 적용했다. 기존 권한 백업은 Git 제외 `.local/ministry/access-backups/`에 있다.
- 기존 `root@daegwangchurch.kr`은 이미 이메일 확인이 완료된 계정이었다. 새 계정 생성·이메일 예외 코드·비밀번호 변경 없이 ADMIN/CARE/출력/보관 전체 권한을 부여했다. 기존 최고관리자는 유지했다.
- `MINISTRY_ACCESS_ENABLED=true`를 로컬 목회 서버 환경에 등록했다. 새로운 운영 배포 주소나 Vercel 프로젝트는 만들지 않았다.
- 재현 가능한 운영 도구: `node scripts/provision-ministry-access.mjs`는 읽기 전용 사전 검사, `--apply`는 실제 적용이다. 완료된 운영에 습관적으로 재실행하지 않는다.
- 런타임은 직접 access_grants 변경이 불가능하며, 고정 search_path와 검증을 가진 제한된 SECURITY DEFINER 함수만 실행한다. 프런트엔드 Supabase API 역할에는 ministry 테이블/함수 권한이 없다.

## 검증

`npm run test:ministry`: 32개 테스트. PostgreSQL 함수/RLS/타 교회 차단/마지막 관리자/무권한 변경/충돌/이메일 확인/초대 재발급·취소·발송 간격/부서 출석·연도 범위/서명 복구 의도 포함. 타입/lint/build/경계 검사 완료. `tests/ministry-access-browser.mjs`는 격리 가상 서버에서 폼과 모바일 화면을 검사하며 POST 응답만 브라우저에서 mock한다. 운영 API에 시험 초대를 만들지 않았다.

실제 root 로그인 후 인증 앱 없이 목회 홈 진입을 확인했다. 2026-10-27 운영 배포와 HTTPS callback 2개 추가, 운영 root 로그인/권한 화면을 사용자 확인했다. Resend SMTP를 연결하고 승인된 기존 관리자 이메일로 비밀번호 찾기 메일 실수신을 확인했다. 신규 초대 수락 전체 흐름은 실제 초대 대상이 정해지면 별도 확인한다. 설정과 수신함 제한은 [deployment.md](deployment.md) 참고.
