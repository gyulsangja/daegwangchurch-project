# 목회활동 중심 통합 관리 재설계

기준일: 2026-10-29. 사용자 요청: 관리자와 목회시스템을 통합하고, 목회활동을 기록하면 홈페이지·앱 운영 자료도 자연스럽게 정리되도록 한다. 이 문서는 목표 구조이며 구현 완료 보고가 아니다.

## 1. 제품 방향과 결정

- `apps/ministry`를 통합 관리 화면의 기반으로 사용한다. 새 앱을 처음부터 만들지 않는다. 명칭은 ‘대광교회 통합 관리’, 최종 대표 주소는 `admin.daegwangchurch.kr`을 목표로 한다. 도메인은 아직 전환하지 않았다.
- 홈페이지·모바일 앱은 사용자용 서비스로 유지한다. 하나의 관리 제품으로 통합하되 공개 서비스와 비공개 목회 데이터의 접근 경계를 유지한다.
- 관리자는 게시판을 골라 같은 내용을 반복 입력하는 대신 예배·활동을 열고 준비, 자료, 진행 결과, 공개를 처리한다.
- 모든 기록을 하나의 거대한 테이블이나 만능 폼으로 합치지 않는다. 예배·교육·행사·돌봄은 전문 화면과 저장 규칙을 유지하고 관련 ID로 연결한다.
- 기존 CMS 원본 ID·게시물 주소·파일·앱 API를 유지한다. 공개 자료를 목회 보관용으로 다시 업로드하거나 복제하지 않는다.
- 내부 기록 저장은 공개가 아니다. 공개 대상 필드와 파일을 확인한 뒤 발행한다. 홈페이지와 앱은 같은 공개본을 사용한다.

## 2. 최상위 메뉴와 진입 경험

| 메뉴 | 첫 화면과 주요 업무 |
| --- | --- |
| 오늘 | 이번 주 예배·활동, 내 담당 요청, 미완료 후속 업무, 발행 대기 자료 |
| 예배·말씀 | 예배별 주보·설교·영상·봉사·출석·내부 기록, 첫시간 묵상 영상 |
| 목회활동 | 계획·일정, 교육·모임·행사, 상담·심방, 목회 기도 |
| 교인·공동체 | 교적·가구, 연간 조직·직분·봉사, 교인 확인·앱 소속 |
| 소식·자료 | 공개 소식, 주보·영상·사진·문서 통합 검색, 홈페이지 안내 |
| 운영 설정 | 사용자·업무 권한, 교회 기본정보, 예배 종류, 조직·직분 체계, 알림·연동 |

권한에 따라 보이지 않는 메뉴가 있고 업무가 적으면 하위 항목을 접는다. ‘접수함’은 오늘 화면의 업무 진입점과 목회활동 내 전용 목록으로 제공한다. 자료실은 원본을 찾아가는 조회 화면이며 별도 복제 저장소가 아니다. 기존 게시판 방식으로 바로 등록하는 기능도 남겨 긴급 공지에 활동 생성을 강요하지 않는다.

오늘 화면은 역할별로 다르다. 콘텐츠 담당자는 이번 주 주보·영상·발행 대기를, 목회자는 만남·후속 돌봄·계획을, 부서장은 담당 부서의 일정·출석을 우선 본다. 권한 없는 기록의 제목·건수·검색 결과도 노출하지 않는다.

## 3. 핵심 업무 흐름

### 주일 예배

1. 예배·말씀에서 ‘이번 주 예배 준비’를 연다. 기본 예배 종류·일시·장소를 제안하되 확정 전에는 새 공개 게시물을 만들지 않는다.
2. 주보를 업로드하고 설교 제목·본문·설교자·영상 링크를 입력한다. 기존 영상이나 주보를 선택해 연결할 수도 있다.
3. 공개 미리보기에서 주보와 말씀을 선택해 발행한다. 같은 자료가 홈페이지·앱에 표시된다. 주보 등록 때문에 별도 공지를 자동 생성하지 않는다.
4. 예배 후 출석·실제 진행·내부 메모·후속 업무를 기록한다. 이 정보는 공개본에 섞이지 않는다.
5. 지난 예배를 날짜·예배 종류·본문·설교자로 찾고 관련 주보·영상·기록을 함께 열람한다. 주간 주보 하나를 오전·오후 등 여러 예배에 연결할 수 있다.

반복 예배 정의와 실제 날짜별 예배 회차를 구분한다. 같은 날 같은 종류의 예배가 여러 번 있을 수 있으므로 날짜만으로 고유성을 결정하지 않는다. 반복 일정 변경은 과거 회차를 바꾸지 않고 미래 회차에만 명시적으로 적용한다.

### 교육·모임·행사

1. 활동을 만들거나 목회 계획에 기존 활동을 연결한다. 대상은 교인·가구·조직을 복수 선택할 수 있다.
2. 일시·장소를 입력하면 일정 초안에 재사용한다. 담당자·준비 메모·명단은 내부 정보다.
3. ‘안내하기’에서 공개용 제목·설명·범위를 확인한다. 필요하면 안내 공지를 추가한다. 활동 하나가 반드시 일정·공지·앨범 세 개를 만드는 것은 아니다.
4. 활동 후 출석·교육 수료·결과·사진을 한 화면에서 처리한다. 교적에는 원본 기록의 연결이 표시되며 사람마다 같은 내용을 입력하지 않는다.
5. ‘소식으로 나누기’에서 공개용 후기와 선택한 사진만 앨범 또는 소식으로 발행한다. 참석자 실명·연락처·내부 평가·사진 공개 미확인 자료는 자동 포함하지 않는다.

### 상담·심방·기도

요청 접수 → 담당 배정 → 일정 → 만남과 결과 → 후속 업무 순서로 진행한다. 교인·가구·조직과 연결해 해당 교적의 허용된 이력에서 조회한다. 상담·심방·개인 대상 목회 기도에는 ‘홈페이지 발행’ 기능 자체를 제공하지 않는다. 공동체에 안내할 내용이 있더라도 별도의 일반 공지를 작성한다. 회원 개인의 묵상·기도는 통합 관리 대상으로 편입하지 않는다.

### 계획과 기록

연간 방향·월간 목표·상시 과제는 기간을 가진 계획으로 관리한다. 계획에 예배·활동·후속 업무를 연결하고 진행 결과를 모아 본다. 모든 활동에 목표 연결을 강제하지 않는다. 계획의 내부 평가와 공개 보고 자료는 별개이며, 건수만으로 목회 성과를 자동 판단하지 않는다.

## 4. 활동 상세 화면

상단: 제목, 기간/일시, 상태, 담당 조직, 다음 할 일. 주요 작업 버튼은 현재 단계에 맞게 최대 2개를 우선 표시한다.

| 화면 | 내용 |
| --- | --- |
| 개요 | 목적·일정·장소·담당·관련 계획·다음 업무 |
| 자료 | 예배는 주보·말씀 우선, 행사는 안내·사진·문서 우선 |
| 참여·기록 | 출석·교육 결과·내부 결과, 업무별 권한 검사 |
| 공개 | 홈페이지·앱 미리보기, 공개 항목·일시·수정 사항·알림 확인 |

돌봄 화면에는 공개 탭이 없다. 소규모 단건 활동은 탭을 최소화하고 빈 항목을 접는다. 모바일은 요약을 먼저 표시하고 등록·편집은 한 작업씩 여는 패널을 사용한다. 목록 검색·필터·스크롤 위치는 상세에서 돌아와도 보존한다. 공개용 제목은 기본 제목을 제안하되 내부 제목과 독립 수정 가능하다.

## 5. 데이터 책임과 관계

| 개념 | 책임 | 기존 자료와의 관계 |
| --- | --- | --- |
| 예배 종류·반복 정의 | 예배 운영 기본값 | 기존 WorshipSchedule과 목회 예배 설정을 조사해 명시적 대응 |
| 실제 예배 회차 | 날짜별 예배 운영·자료 연결 | 신설 필요. 주보·말씀·출석을 회차 ID로 연결 |
| 일반 활동 | 교육·모임·행사의 운영 단위 | 기존 목회 계획/활동을 보존하며 전문 유형 확장 |
| 계획 | 기간·목표·연결 활동·평가 | 기존 GOAL/PLAN 유지, 별도 강제 재입력 없음 |
| 돌봄 기록 | 상담·심방·기도와 후속 | 기존 비공개 목회 도메인 유지 |
| 공개 콘텐츠 | 외부 표시할 내용·파일·공개 상태 | Bulletin/WorshipContent/Event/Notice/Album 원본 유지 |
| 활동-자료 연결 | 교회, 원본 종류/ID, 연결 용도, 버전 | 현재 EVENT/NOTICE contentLinks에서 확장 |
| 참여 결과 | 출석·수료·봉사 실적 | 기존 목회 전문 기록을 참조, 교적에서 역조회 |
| 공개 변경 이력 | 승인한 공개 필드·파일 버전·발행자 | 주보 등 없는 모델부터 단계적 추가 |
| 후속 업무 | 담당자·기한·상태·관련 원본 | 단순 업무, 상담 원문을 작업 제목에 복사하지 않음 |

주보와 예배 회차는 다대다, 말씀 영상도 복수 회차 연결 가능하도록 설계한다. 첫시간 묵상은 예배 회차 없이 날짜별 콘텐츠로 등록할 수 있다. 활동과 자료는 고정 ID로 연결하고 동일 제목을 허용한다. 다른 교회 원본 연결은 서버에서 거부한다.

현재 Bulletin에는 worshipContentId가 있지만 이 관계만으로 예배 회차·다중 예배·출석을 표현할 수 없다. 기존 관계를 삭제하지 않고 새 회차/연결 모델을 보강한다. 유튜브에서 수집된 영상은 영상 ID와 기존 콘텐츠 ID로 중복을 확인하고 회차 후보를 제안한다. 제목·날짜 유사성만으로 자동 연결하지 않는다.

## 6. 저장·공개·보관·알림

- 활동 상태(준비/진행/완료/취소)와 자료 공개 상태(초안/검토/예약/공개/철회)를 분리한다. 내부 보관 상태와 삭제 상태도 구분한다. 이것은 목표 상태이며 현재 DB enum에 모두 존재하지 않는다.
- 공개 API는 허용 필드만 반환한다. 내부 객체를 통째로 직렬화한 뒤 일부 필드를 지우는 방식은 사용하지 않는다.
- 내부 변경은 공개본을 자동 덮어쓰지 않는다. 공개 화면에 ‘수정사항 있음’을 보여주고 재발행 때 반영한다. 공개 편집 화면에서 저장할 때도 결과를 명확히 안내한다.
- 일시·장소 변경과 취소는 기존 공개 일정과 앱 저장 일정에 연결된 ID를 유지한다. 취소 안내와 비공개 철회는 별도 작업이다. 과거 결과 기록은 지우지 않는다.
- 파일은 불변 버전으로 저장한다. 주보 교체 시 기존 파일을 덮어쓰지 않고 새 버전을 만든다. 공개 철회 후에도 과거에 공개·다운로드된 파일 회수는 보장하지 않는다. 내부 전용 파일은 처음부터 비공개 저장소와 권한 확인 다운로드를 사용한다.
- ‘예배/활동 저장’은 푸시 발송이 아니다. 발행 때 알림 여부·대상·시간·내용을 확인하고 콘텐츠 ID+발행 버전+대상으로 중복을 막는다. 실패·재시도·발송 결과를 표시한다.
- 현재 기존 워커는 공개 이벤트/중요 공지를 자동 발송할 수 있다. 새 발행 화면 전환 전에 기존 트리거와 새 발송 요청 경로를 함께 정리해야 한다. UI만 바꿔 자동 발송이 꺼졌다고 표시하지 않는다.
- 공개 반영은 서버에서 처리한다. 공개 원본과 작업 이벤트를 같은 트랜잭션으로 기록하거나 실패 복구 가능한 작업 큐를 사용한다. 처리 중/실패/반영 완료를 구분하고 실패한 상태를 완료로 표시하지 않는다.

## 7. 권한과 통합 로그인

하나의 로그인 진입점에서 업무 권한·담당 범위·정보 민감도를 검사한다. 기존 CONTENT 역할은 일정·공지 전용으로 활성화된 상태이며, 주보·말씀 권한까지 자동 확대하지 않는다. 확장 권한과 기존 CMS 권한의 전환은 영향 미리보기 후 적용한다.

- 콘텐츠 담당: 허용된 공개 자료 작성·편집·발행. 교적·출석 명단·돌봄 원문 접근 없음.
- 행정 담당: 교적·조직·접수·예배 운영. 돌봄 원문·반출은 별도 권한.
- 부서 담당: 지정 조직·연도의 활동·출석·교육. 범위 밖 교인 자료 없음.
- 목회 담당: 배정된 대상의 계획·돌봄·결과. 민감 기록의 개별 제한 우선.
- 당회원: 승인된 운영 자료·집계. 직분만으로 개인정보 접근권한 부여 없음.
- 권한 관리자: 초대·권한·회수·감사. 권한 관리와 상담 원문 열람을 별개로 설계.

업무별 조회/작성/발행/출력/삭제를 분리하고 복수 역할을 허용한다. 한 역할의 넓은 범위를 다른 역할의 민감 업무에 전파하지 않는다. 메뉴·검색·API·첨부 다운로드·출력 모두 같은 정책을 적용한다. 기존 최고관리자 권한을 임의 변경하지 않는다.

## 8. 구현 구조와 성능

- apps/ministry: 통합 업무 UI와 인증된 서버 진입점. apps/admin: 전환 중 기존 CMS와 공개/회원 API 유지. apps/website·mobile: 기존 이용자 경험 유지.
- packages/contracts: 업무 입력, 최소 공개 DTO, 자료 참조, 권한 계약. packages/server: 콘텐츠 편집·발행·접수 서비스. packages/ministry-core: 목회 활동·교적·범위 정책. packages/database: 스키마·마이그레이션·저장 어댑터.
- 앱 사이 소스 직접 import 금지. 도메인 서비스 공유는 서버 패키지를 통해 수행한다. 공개 서버가 ministry 스키마 전체 권한을 갖게 하지 않는다.
- 목록은 요약·페이지 단위로 조회하고 교적 상세를 행마다 반복 조회하지 않는다. 화면 틀과 목록 스켈레톤을 먼저 표시한다. 자료·참여자·변경 이력은 해당 영역을 열 때 불러온다.
- 공개 콘텐츠는 공개 전용 캐시/무효화 전략을 사용하고 사용자별 비공개 응답은 공유 캐시에 넣지 않는다. 권한 회수는 다음 요청부터 반영한다.
- 향후 타 교회 서비스 확장을 위해 새 연결·업무 키에 churchId를 포함한다. 현재 공개 CMS는 단일 교회 모델이므로 교회별 데이터 격리 마이그레이션 전에는 다중 교회 서비스가 가능하다고 표시하지 않는다.

## 9. 이전 순서와 완료 조건

| 단계 | 산출물 | 완료 조건 |
| --- | --- | --- |
| 1 구조 확정 | 이 설계·기존 기능 대응표·화면 흐름 | 기존 기능 누락과 공개 경계 검토 |
| 2 예배 통합 첫 단위 | 예배 회차 + 주보·영상 연결/편집/공개 + 기록 조회 | 한 번 등록 → 웹·앱 동일 원본 → 예배 기록에서 재조회 |
| 3 활동 통합 | 계획·행사·교육·사진·출석 연결 | 결과 한 번 기록 → 대상 교적에 권한별 표시 |
| 4 업무 통합 | 접수함·상담 인계·교인 확인·연간 소속 | 중복 인계 방지, 원본 상태 회신, 연도 전환 검증 |
| 5 관리 기능 이전 | 홈페이지 안내·모든 콘텐츠·운영 설정·권한 | 기존 CMS 기능별 등록/수정/공개/첨부/알림 동등성 |
| 6 전환·정리 | 대표 주소·기존 주소 이동·중복 화면 종료 | API/예약 작업/푸시/업로드 의존 확인, 복구 경로 검증 |

각 단계는 격리된 자료로 검증 후 운영 적용한다. 운영 DB 변경은 검토 가능한 SQL·백업/복구 절차를 준비하여 승인 후 적용한다. 기존 콘텐츠 연결은 확실한 ID를 우선하고 불확실한 후보는 검토 목록에 둔다. 새 예배 회차를 만들기 위해 기존 주보나 영상의 날짜를 일괄 수정하지 않는다.

기존 관리자를 종료하기 전 기존/신규 원본 건수·ID·파일 참조, 페이지 주소, 로그인 복귀 주소, 공개/비공개·예약, 앱 저장 콘텐츠, 푸시 중복, 업로드 실패, 동시 편집 충돌, 권한 회수, 인쇄/다운로드를 확인한다. 먼저 기존 편집 진입을 새 화면으로 전환하고 API/작업 실행부는 의존 제거가 확인될 때까지 유지한다. 되돌리기는 화면 진입점을 복원하는 것으로 가능해야 하며 데이터 이중 쓰기를 기본 전략으로 삼지 않는다.

## 10. 현재 구현과 차이

완료: 목회 화면에서 일정·공지 원본 편집, 목회 계획에 공개 일정·공지 ID 연결, CONTENT 역할과 제한, 기존 CMS 원본 유지. 예배 회차 기록·출력, 주보·말씀 직접 등록/수정/연결/공개, 주보 PDF 이전 파일 보관·복원, 자료 삭제(파일 보존)를 구현·배포했다. 문의·돌봄 통합 접수함, 앱 회원 승인·직분·소속·관리자 권한·삭제, 모임별 공지·공식 소속 일괄 관리·공지 담당자 관리를 구현했다. 예배 회차에 기존 출석부를 연결하고 날짜·예배별 출석 화면으로 이동하며 출력할 수 있다. 최신 배포 상태는 HANDOFF를 따른다.

남은 범위: 활동→공개 초안 생성, 공개 변경 승인/푸시 분리, 세부 복수 역할, 접수 담당 배정·홈페이지 문의 목회 인계, 연간 조직-앱 소속 동기화, 모든 CMS 기능 동등성 확인 및 기존 관리자 종료. 예배 출석 원본은 기존 출석부를 유지한다.

첫 구현 단위는 **‘예배 한 회차에서 주보와 말씀을 등록·연결하고 공개한 뒤 다시 찾아보기’**다. 이 흐름을 완성한 뒤 활동 유형을 확장한다. 프레임워크 교체·전면 재작성·기존 관리자 선삭제는 진행하지 않는다.
