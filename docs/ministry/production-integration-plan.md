# 운영 연결 설계와 실행 순서

2026-10-25 후속 구현 상태: 서버 로그인·세션 갱신, 운영 권한 조회, PostgreSQL 트랜잭션 어댑터와 별도 SQL, 기존 확인된 회원의 교적 연결, 상담 접수 메타데이터의 목회 일정 인계, CMS 바로가기를 구현했다. 실제 운영 관리자/DB 구성 응답과 환경설정은 대기 중이다. 소속·접수 상태의 양방향 자동 동기화는 활성화하지 않았고 기존 CMS에서 승인/상태 변경한다. 아래 최종 모델 중 연도/가구 등 일부는 개별 행 JSON으로 보존하며 세부 정규화는 남아 있다. 최신 제한과 적용 절차는 HANDOFF 및 packages/database/ministry/README.md 참조.

2026-10-25. 아래는 구현할 설계안이다. 운영 인증·DB·홈페이지 연동을 완료했다는 문서가 아니다. 현재 목회 앱은 로컬 가상 자료만 사용한다.

## 자료의 책임

| 자료 | 관리하는 시스템 | 연결 방식 |
| --- | --- | --- |
| 회원 계정·인증 | 기존 인증 서비스 | 검증된 계정 ID 참조, 이메일/이름으로 자동 연결하지 않음 |
| 교적·가족·직분·연도별 소속 | 목회시스템 | 교회 ID와 교인 ID를 독립 유지 |
| 공지·주보·설교 | 기존 CMS | 기존 원본 유지, 초기에는 관리 화면 링크 제공 |
| 상담·심방 접수 | 기존 앱/API | 접수 ID를 기준으로 명시적 담당자 인계 |
| 상담 내용·후속 일정·목회 기도 | 목회시스템 | 공개 홈페이지/API로 복제하지 않음 |
| 성도의 개인 기도·묵상 | 기존 앱 개인 영역 | 목회시스템에 연결하지 않음 |

## 운영 DB 모델 초안

packages/database에 운영 CMS와 구분되는 목회 스키마·전용 역할을 준비한다. 기존 Prisma 모델이나 운영 DB에 이 문서만으로 변경을 적용하지 않는다.

- Church, MinistryAccessGrant: churchId + 검증된 authUserId, 권한, 대상 조직 범위, 부여/회수 시각. 기존 CMS 관리자 권한으로 자동 부여하지 않는다.
- Member, Household, HouseholdMember: 계정 없는 교인 지원, 가족 관계의 기준 인물과 유효 기간.
- MemberAccountLink: churchId/memberId/authUserId, 승인자·승인 시각·해제 이력. 활성 연결의 중복 방지, 동명이인 수동 확인.
- MinistryYear, Organization, OrganizationRole, Assignment: 연도별 편성 및 변경 이력. 교인 직분과 조직 역할 분리.
- WorshipService, AttendanceSession, AttendanceParticipant, AttendanceRevision: 예배 ID/회차/대상자 명단/미확인 포함 상태. 첫 저장 명단 보존, 추가·제외는 사유와 version을 가진 별도 작업. 이번 로컬 구현은 날짜+예배 이름+조직으로 회차를 식별하며 예배 ID 카탈로그는 후속.
- CareIntakeLink, CareEncounter, CareFollowUp: 외부 접수 ID의 교회별 고유 제약, 담당자, 일정·수행 기록. 원본 접수와 내부 상담 기록을 구분.
- PastoralPrayer, MinistryGoal, MinistryAction, ProgressEntry: 목표와 실행 연결, 수행 기록과 변경 전 내용 보존.
- AuditEvent, IntegrationOutbox: 민감 본문을 제외한 변경/열람 감사 및 재시도 가능한 연동 이벤트. DB 변경과 outbox 기록을 같은 트랜잭션으로 저장.

모든 소유 데이터에 churchId를 두고 교회 ID를 포함한 복합 FK로 타 교회 참조를 차단한다. 서버는 사용자 입력 churchId를 신뢰하지 않고 검증된 권한에서 결정한다. API의 조회/목록/통계/내보내기에 동일한 범위 검사를 적용한다. DB 연결 역할은 필요한 스키마와 동작만 허용한다.

## 권한 분리

운영에서는 교적 조회/수정, 출석 기록(조직 범위), 돌봄 조회/기록(담당 범위), 목회 계획, 사용자 권한 관리, 반출을 별도 권한으로 나눈다. 현재 로컬 ADMIN/OFFICE/LEADER + CARE는 검토용이며 이 권한 모델의 운영 구현으로 취급하지 않는다. 권한 회수는 다음 요청부터 적용하고 긴 세션의 캐시로 우회되지 않게 검증한다.

## 연결 순서와 완료 기준

1. 검증된 로그인 → 목회 권한 확인 → 교회 범위 결정. 권한 없는 기존 관리자와 일반 회원은 접근 거부. 로컬 가상 액터를 운영에서 사용할 수 없어야 한다.
2. 정규화 DB 어댑터 구현. 실패 롤백, 동시 수정 충돌, 다른 교회 ID, 권한 회수, 백업 복원 검증. 현재 SQLite 스냅샷은 운영 이관 대상으로 자동 취급하지 않는다.
3. 교인 확인 요청을 교적에 연결. 담당자가 후보와 연락처를 확인한 뒤 승인. 기존 계정 연결을 바꾸는 경우 명시적 해제와 이력 보존. 홈페이지와 앱에는 승인 상태·허용된 소속 정보만 전달.
4. 상담 접수 가져오기. 동일 접수 재전송에도 한 건만 생성. 담당자 인계 후 일정·수행·후속 관리. 회원에게는 접수/처리 상태만 전달하며 상담 본문·내부 기도·수행 기록은 제외.
5. CMS 진입 링크 통합. 공지·주보·설교 편집 기능을 복제하지 않으며 기존 발행 원본 유지.

운영 반영 전 실제 담당 권한, 기록 보존/삭제 범위, 백업 보관·복구 책임을 확정한다. 기존 앱 상담 보관 설정을 새 목회 전체 기록에 자동 적용하지 않는다. 실제 마이그레이션·배포는 적용 내용과 복구 절차를 검토한 뒤 진행한다.
