# 통합 로그인·관리자·업무 권한 전환

현재 구현과 운영 전환 범위는 [통합 관리 운영 전환](unified-management-release.md)을 우선한다. 아래 8개 역할 묶음은 후속 목표이며, 현재 구현은 5개 목회 역할 및 독립 CMS 권한의 통합 편집이다. 아래 ‘현재 문제’는 전환 전 진단 기록이다.

2026-10-30 사용자 추가 요구를 반영한 구현 기준. 아래 목표 권한은 아직 운영 권한으로 일괄 적용하지 않았다. 기존 CMS 권한과 목회 권한을 모두 가진 운영자의 접근도 유지한다.

## 현재 문제

- Supabase 계정 원본은 같지만 CMS의 기본 인증 쿠키와 목회의 `ministry-auth` 쿠키, 서비스 주소가 달라 브라우저 로그인 상태가 따로 유지된다.
- CMS `admin_profiles`와 목회 `access_grants`를 별도로 관리한다. 통합 콘텐츠 API가 두 권한을 동시에 요구해 한쪽 승인만으로는 사용할 수 없다.
- CONTENT는 현재 일정·공지에만 접근한다. 화면 이름이 홈페이지·앱 운영자여도 모든 콘텐츠를 관리하는 역할은 아직 아니다.
- 상담 접수 담당자 지정과 목회 민감 기록 권한도 별개다. 두 정보를 무조건 합치면 원치 않는 상담 열람 권한이 생길 수 있다.

## 최종 사용자 흐름

통합 관리 진입 → 한 로그인 화면 → 본인 담당 업무 홈. 관리자 별도 회원가입은 제공하지 않고 기존 회원 계정을 지정하거나 초대한다. 교인 확인/직분/전도회 역할은 시스템 권한을 자동 부여하지 않는다. 앱 회원 로그인은 유지하며 관리자 웹 세션을 앱에 공유하지 않는다.

한 관리 도메인과 서버 전용 HttpOnly 세션을 사용한다. 로그인 복귀 경로는 같은 관리 도메인의 허용 경로만 인정한다. 이전 관리자 로그인/편집 링크는 기능 이전 후 대응하는 통합 경로로 보낸다. 광범위한 최상위 도메인 쿠키 공유 또는 URL에 토큰을 넣는 방식으로 해결하지 않는다.

## 역할은 편의용 묶음, 판정은 업무와 대상 범위

| 역할 묶음 | 기본 업무 | 기본 제외 |
| --- | --- | --- |
| 시스템 관리자 | 사용자 초대·권한·접근 중지·운영 설정·감사 | 상담/기도 원문 자동 열람 |
| 담임목회 담당 | 전체 교적·목회 계획·배정된 돌봄·예배·통계 | 시스템 권한 변경 자동 허용 |
| 담당 교역자 | 지정 조직·교인의 교적·목회 활동 | 담당 밖 민감 기록 |
| 교회 행정 | 교적·가구·직분·조직·교육·일반 문의 | 상담·기도 원문 |
| 홈페이지·앱 편집 | 공지·일정·말씀·주보·사진·공개 소개 초안 | 교적/상담·권한 설정·자동 발행 |
| 발행·알림 담당 | 검토된 공개 자료 발행·예약·발송 확인 | 내부 기록 공개 전환 |
| 부서 담당 | 지정 연도/조직 명단·출석·교육·모임 소식 | 전체 명부·다른 부서 |
| 당회 열람 | 허용된 운영 현황·요약 보고 | 개인 상담·기도·연락처·기본 수정 |

한 사람에게 여러 묶음을 지정할 수 있다. 역할마다 담당 범위를 함께 보관한다. 편집 역할의 전체 교회 범위를 담당 교역자의 상담 권한에 합쳐서 적용하지 않는다. 부서 담당은 연도 전환 때 재확인하며 만료 기간을 설정할 수 있다.

업무 능력은 조회/작성/수정/발행/푸시/삭제/출력·내보내기를 구분한다. 상담 접수 설정 권한은 상담 원문 열람 권한과 다르다. 앱의 개인 묵상·기도는 이 권한 구조로도 열람하지 않는다.

## 통합 관리자 설정

`설정 → 사용자·권한`: 계정 검색/초대, 역할 복수 선택, 역할별 담당 조직·기간, 실제 허용 화면 미리보기, 이용 중지, 변경 사유·이력. 계정 삭제와 관리자 권한 해제는 별도 동작이다. 본인 잠금과 마지막 시스템 관리자 제거를 막는다. 민감 권한 변경은 비밀번호 재확인 또는 설정된 2단계 인증을 요구한다.

`설정 → 운영 정책`: 교회 공개 정보, 접수 열기/닫기·담당자·보관 기간, 공개·알림 정책, 파일/변경 이력, 서비스 연결 상태. 일반 콘텐츠 작성 화면에 시스템 설정을 섞지 않는다.

## 전환과 검증 순서

1. 기존 CMS/목회 계정 권한을 읽기 전용으로 대조하고 미연결 계정·차이를 표시한다. 이름이 아닌 Supabase 사용자 ID로 매칭한다.
2. 권한 계약·서버 판정·대상 범위·권한 UI를 격리 테스트한다. 기존 권한은 자동 확대하지 않는다.
3. 필요한 운영 SQL과 복구 절차를 준비하고 별도 승인 후 적용한다. 본 전환은 기존 예배/주보 테이블 승인 범위에 포함되지 않는다.
4. 메뉴, API, 상세/파일/출력, 공개/푸시 모두 같은 권한 판정을 적용한다. 기능이 빠진 이전 화면은 먼저 대체한다.
5. 기존 최고관리자/운영자/부서 담당/권한 없는 회원의 로그인·접근·회수를 검증하고 통합 주소로 전환한다.
6. 기존 관리자 UI를 종료하되 공개 API와 예약 작업은 의존 확인 후 유지 또는 이동한다. 홈페이지·앱의 기존 자료 ID와 URL을 바꾸지 않는다.

완료 조건: 일반 운영자가 기존 CMS를 열지 않고 모든 담당 업무를 처리하고, 사용자 및 권한 설정도 한 화면에서 끝나며, 권한 없는 경로를 직접 호출해도 차단되는 상태.
