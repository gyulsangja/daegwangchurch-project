# 계정 출시 검증용 Supabase 환경 구성안

2026-11-16 갱신. 사용자 승인으로 테스트 프로젝트를 생성하고 계정 통합 검증을 실행했다. [실행 결과](release-test-2026-11-16.md)를 먼저 확인한다. 아래는 생성 전 구성안이다.

2026-11-15. 사용자 확인: 별도 테스트 프로젝트 없음. 아래는 준비안이며 프로젝트 생성·결제·SMTP 변경·메일 발송·원격 DB 적용을 실행한 기록이 아니다.

## 권장 구성

- 이름 후보 `daegwang-release-test`. 운영과 다른 project ref를 가진 빈 프로젝트. 운영 DB·회원·사진·상담·인증 계정 복제 금지.
- 가능하면 기존 계정의 Free 조직/잔여 무료 슬롯 사용. 현재 요금제·사용량은 미확인. Free는 활성 프로젝트 최대 2개, 1주 비활성 시 일시정지 안내가 있다. 유료 조직의 추가 프로젝트는 비용이 발생할 수 있으므로 무료라고 가정하지 않는다.
- API와 Expo 웹은 우선 localhost에서 실행한다. 별도 Vercel 배포·도메인·스토어 계정은 이 검증에 필요하지 않다. Supabase만 원격 테스트 프로젝트를 사용한다.
- 테스트 환경 파일은 별도 무시 경로 `.local/release-test/`에 저장. 기존 apps/*/.env.local 덮어쓰기 금지. 개발 서버 실행 시 명시적으로 테스트 설정을 주입하고 기존 환경 파일 로딩보다 우선하는지 확인한다.
- 실행 전 Supabase URL·DB host/project ref·API 포트·앱 공개 설정이 모두 같은 테스트 프로젝트를 가리키는지 비교한다. 운영 project ref와 일치하면 실행을 중단한다. `.invalid` 가상 자료 외 실제 메일 검증용으로 승인된 수신 주소만 예외 사용.

## 로컬 사전 검사

`node scripts/check-release-test-env.mjs .local/release-test/targets.json`을 실행한다. JSON에는 `TEST_SUPABASE_PROJECT_REF`, `NEXT_PUBLIC_SUPABASE_URL`, `EXPO_PUBLIC_SUPABASE_URL`, `DATABASE_URL`, `DIRECT_URL`, `EXPO_PUBLIC_API_URL`을 넣는다. 비밀 DB URL이 포함되므로 Git에 추가하지 않는다. 검사기는 입력값을 출력하거나 서버에 접속하지 않는다. 운영 project ref, 서로 다른 프로젝트, SSL 미설정, 외부 API 주소, DB host를 덮어쓰는 쿼리 매개변수는 거부한다.

이 검사는 입력 JSON의 URL 일관성만 확인한다. 공개 키·서버 키의 실제 소속, 요금제, 런타임에 주입된 최종 설정이나 DB 권한은 보증하지 않으며 마이그레이션 실행기에 자동 연결되어 있지 않다. 실행 직전에 실제 주입 설정과 대조한 뒤 승인된 절차로 진행한다. 회귀 검사: `node --test tests/release-test-env.test.mjs`.

## 생성 승인 후 순서

1. 대시보드의 조직 요금제·무료 슬롯·생성 화면 예상 금액을 확인한다. 대상과 예상 비용을 제시하고 프로젝트 생성 승인을 받는다. 무료 슬롯이 없으면 유료 전환을 실행하지 않는다.
2. 별도 비밀번호/서버 키를 안전한 로컬 파일 또는 비밀 저장소로 관리한다. 채팅·Git·EXPO_PUBLIC 변수에 비밀값 금지. 새 프로젝트의 DB 접속정보와 공개 인증키를 혼동하지 않는다.
3. 테스트 DB에 저장소의 public migration과 ministry SQL을 순서대로 적용한다. ministry는 비공개 스키마로 유지한다. 새 009의 선행 FK·권한·기존 고아 연결 검사를 포함한다. 새 원격 환경 적용도 승인 범위를 먼저 확인한다.
4. 가상 교인 두 명과 가상 상담·소속·기도만 구성한다. 한 명 삭제 시 다른 회원 및 독립 교적이 유지되는지 검증한다. 운영 관리자 권한을 복사하지 않는다.
5. 이메일 즉시 가입 설정, 승인된 localhost 복귀 URL, 실제 앱이 읽는 정책/삭제/복구 설정을 테스트 환경에만 설정한다. 삭제 worker는 테스트 환경을 명시한 수동 실행부터 검증하고, 동작 확인 후 테스트용 주기 실행과 오류 관측을 검증한다.
6. 메일: 기본 SMTP는 프로젝트 팀원 주소 등 제한이 있어 사용 가능한 범위를 공식 문서와 대시보드에서 확인한다. 일반 테스트 수신자가 필요하면 별도 발송 전용 SMTP 설정과 권한을 승인받는다. 기존 운영 SMTP 키를 무단 재사용하지 않는다. 실제 발송은 수신자·종류·횟수 승인 후 수행한다.

## 합격 기준

| 검증 | 확인할 결과 |
| --- | --- |
| 가입 | 이메일 인증 없이 일반 회원 생성, 약관/14세 확인, 중복 요청 안전 처리 |
| 복구 | 승인된 수신자에게 메일 도착, 올바른 OTP만 허용, 만료·재사용 거부, 이전 비밀번호/갱신 세션 무효 |
| 탈퇴 | 본인 재인증, 개인 자료·교인 확인·앱 상담·목회 연결/파생 일정 삭제, 다른 회원 유지 |
| 제공자 삭제 | worker가 실제 Auth 계정을 삭제, 실패 시 재시도, 접수와 완료 구분 |
| 잔여 토큰 | 발급된 JWT가 즉시 만료됐다고 가정하지 않고, 탈퇴 tombstone/사용자 검증으로 개인 API 접근 차단 확인 |
| 복원 | 가상 백업 복원 후 삭제 목록을 대조해 재삭제하고 외부 공개 전 조회/로그인 차단 확인 |

기존 로컬 테스트 성공은 위 실제 Auth/메일 검증을 대신하지 않는다. 테스트 프로젝트 복원 성공도 운영 백업 상품의 실제 보관 설정·복원 가능성 검증과 별개다. 운영 적용 전 백업/로그/영수증 기간과 목회 권한 계정의 보호 절차를 확정한다.
